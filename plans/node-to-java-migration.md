# Node → Java 业务迁移规划

> 把 `D:\personal-item\uniAppNode` 的业务完整迁移到 `D:\personal-item\imgJava`。
>
> **单向迁移**：`uniAppNode` 是只读的事实来源，`imgJava` 是唯一的写入目标。
> 本规划中的任何步骤都不修改 Node 项目；对它的动作只有「读取」与「只读执行以产出参照值」。

---

## 1. 目标与硬约束

目标：**行为等价的 Java 实现**，前端（uniApp）一行不改。

由「前端不改」推出的硬约束，任何设计决策与此冲突时以本节为准：

| 约束 | 说明 |
|---|---|
| 响应信封不变 | `{ code, data, message }`，成功与失败同一形状 |
| 业务错误一律 HTTP 200 | 401/403/404/409/422/429 全放 `code`；**只有未处理异常是 500** |
| 端点路径与字段名不变 | 含 `objectKey`、`publicUrl`、`nextCursor`、`previousImageDeleted`、`imageDeleted` 等 |
| 错误文案不变 | 如 `用户名或密码错误`、`Missing Bearer token`、`Invalid or expired token`、`已退出登录`、`注册暂未开放` |
| 时间字段格式不变 | 仍是 `YYYY-MM-DD HH:MM:SS` 的 UTC **裸字符串**，不得变成 ISO 8601 或带时区 |
| 上传仍是 multipart POST | 签名算法与两条 Condition（`eq $Content-Type`、`content-length-range 1..10MB`）不变 |

## 2. 已确认的决策

| # | 决策 | 影响 |
|---|---|---|
| 1 | **持久化用 `JdbcClient`，不用 JPA** | 可删 `spring-boot-starter-data-jpa`；SQL 与原实现逐条对照；Flyway 独占 schema 所有权 |
| 2 | **使用 Spring Security 过滤器链** | 必须额外实现 4 项才能保住 HTTP 200 信封，见 §8 |
| 3 | **不复刻 `RateLimit` 响应头** | 已确认前端不读；在文档中记录此差异 |
| 4 | **允许只读执行 Node 代码产出参照值** | POST policy 签名与 bcrypt 可做逐字节对照；每次执行后用 `git status` 证明 Node 工作区仍干净 |
| 5 | **不迁移现有数据，建空库** | 无需 SQLite → PG 数据搬运；MinIO 桶内旧对象会变成孤儿，需在上线前单独处置 |

### 决策 2 的一个前提说明

选择了 Spring Security，就意味着 §8 那张表里的工作**必须**做完。若实际只想用它的 `BCryptPasswordEncoder` 而不要过滤器链，可退回「手写一个约 40 行的 `OncePerRequestFilter`」方案，工作量显著减少。**此项待最终确认。**

## 3. 技术映射

| Node | Java |
|---|---|
| Express 5.2 | Spring Boot 4.1.1 `spring-boot-starter-webmvc` |

| `middleware/auth.js` 的 `requireAuth` | Spring Security 自定义过滤器 + entry point |

| `bcryptjs` cost 12 | `BCryptPasswordEncoder(12)` |
| `crypto.randomBytes(32).toString('base64url')` | `SecureRandom` 32 字节 + Base64 URL 编码（**无填充**） |
| `crypto.createHash('sha256').digest('base64url')` | `MessageDigest` SHA-256 + Base64 URL（**无填充**） |
| `crypto.randomUUID()` | `UUID.randomUUID()` |
| `sqlite3` + 手写 SQL | `JdbcClient`（`spring-boot-starter-jdbc`） |
| `express-rate-limit` MemoryStore | Bucket4j + Caffeine（进程内） |
| `@aws-sdk/client-s3` | `software.amazon.awssdk:s3` |

| `node:test` + Supertest | JUnit 6 + MockMvc（项目已具备） |

### 3.1 时间函数的映射（最容易出错的一类）

Node 里全部时间由 SQLite 产出为 `YYYY-MM-DD HH:MM:SS`。Java 侧统一为：
**列类型 `timestamp`（不带时区），写入/比较一律用 `now() at time zone 'utc'`。**

| Node（SQLite） | Java（PostgreSQL） |
|---|---|
| `CURRENT_TIMESTAMP` / `datetime('now')` | `now() at time zone 'utc'` |
| `datetime('now', '+900 seconds')` | `(now() at time zone 'utc') + make_interval(secs => ?)` |
| `datetime('now', '-1800 seconds')` | `(now() at time zone 'utc') - make_interval(secs => ?)` |
| `datetime(?, 'unixepoch')` | `to_timestamp(?) at time zone 'utc'` |
| `datetime(expires_at) > datetime('now')` | `expires_at > (now() at time zone 'utc')` |
| `ORDER BY id DESC LIMIT ?` | 同名 |
| `LIKE ? ESCAPE '\'` | 同名（显式写 `ESCAPE` 保持可读） |
| `INSERT OR IGNORE` | `INSERT ... ON CONFLICT DO NOTHING` |
| `AUTOINCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` |

> 读出时必须格式化为 `YYYY-MM-DD HH:MM:SS` 再进响应体。**这是契约的一部分**，不是实现细节。

## 6. 数据库设计

新增 `V2__create_core_tables.sql`（**不改已存在的 `V1__baseline.sql`**），**表名与列名与 SQLite 完全一致**，这样两边可以逐条对照：

| 表 | 要点 |
|---|---|
| `users` | `id` IDENTITY、`username` UNIQUE、`password_hash`、`created_at` |
| `refresh_tokens` | `token_hash` UNIQUE、`user_id` FK `ON DELETE CASCADE`、`expires_at`、`created_at` |
| `token_blacklist` | `jti` PRIMARY KEY、`expires_at`、`revoked_at` |
| `files` | `object_key` UNIQUE、`user_id` FK `ON DELETE CASCADE`、`content_type`、`size`、`created_at` |
| `banners` | `id`、`name`、`image_object_key`、`enabled`（0/1）、`created_at` |

索引照搬：`idx_files_user_id(user_id, id)`、`idx_refresh_tokens_hash(token_hash)`、`idx_token_blacklist_expires_at(expires_at)`。

`enabled` 保留 0/1 整数（不改成 boolean）—— 契约里是 JSON 布尔，但存储层改成 boolean 会引入无谓的映射差异。

## 7. 端点清单（14 个）

| # | 方法 + 路径 | 鉴权 | 限流 | 备注 |
|---|---|---|---|---|
| 1 | `GET /health` | 无 | 无 | 只表示进程存活（Node 亦然） |
| 2 | `POST /auth/register` | 无 | 无 | 默认关闭 → `code 403` |
| 3 | `POST /auth/login` | 无 | IP + 账户 | 双维度 |
| 4 | `POST /auth/refresh` | 无 | 无 | 事务内轮换 |
| 5 | `POST /auth/logout` | **路由内自校验** | 无 | 见 §9 |
| 6 | `GET /me` | Bearer | 无 | |
| 7 | `POST /files/upload-url` | Bearer | 每用户 | 签发 POST policy + 落记录 |
| 8 | `GET /files` | Bearer | 无 | 游标分页 |
| 9 | `POST /files/delete` | Bearer | 无 | 整批归属校验 |
| 10-14 | `/banners` POST / GET列表 / GET单个 / PATCH / DELETE | Bearer | 无 | 5 个方法 |

> **注意 #5**：Node 的 `/auth/logout` **没有走 `requireAuth` 中间件**，它在路由内部自己解析 Bearer、自己 verify、自己返回 `Missing Bearer token` / `Invalid or expired token`。Java 侧必须复刻这个结构 —— 若交给 Spring Security 过滤器处理，文案和返回时机会变。因此 `/auth/**` 在过滤器链上应为 `permitAll`，鉴权在 controller 内完成。

## 8. Spring Security 的契约保全（决策 2 的代价）

`spring-boot-starter-security` 的默认行为会直接破坏 §1 的硬约束。必须全部处理：

| 项 | 处理 |
|---|---|
| 未认证 | 自定义 `AuthenticationEntryPoint` → `HTTP 200` + `{code:401, data:null, message:"Invalid or expired token"}` |
| 无权限 | 自定义 `AccessDeniedHandler` → `HTTP 200` + `{code:403, ...}` |
| CSRF | `disable()`（纯 JSON API，无 Cookie 会话） |
| `formLogin` / `httpBasic` | `disable()` |
| `logout` | `disable()`（业务自带 `/auth/logout`，语义完全不同） |
| Session | `STATELESS` |
| `WWW-Authenticate` 头 | 确保不出现 |
| `authorizeHttpRequests` | 精确到路径：`/health`、`/auth/**` 放行；`/me`、`/files/**`、`/banners/**` 需认证 |
| Bearer 解析 + 黑名单查询 | 自定义 `OncePerRequestFilter`，文案与 Node 一致 |

**兜底措施（不可省）**：一条契约测试，遍历**所有端点 × 所有失败路径**（未认证 / 无权限 / 不存在 / 冲突 / 限流 / 参数错），断言 `HTTP status == 200` 且响应体形状正确。任何 Spring Security 的默认行为漏出来都会在这里被抓到。

## 9. 相对 Node 的行为修正（唯一一处）

**`/auth/logout` 失败路径的副作用。** Node 版先拉黑 access token（写 `token_blacklist`）再校验 refresh token；因此传一个**有效** access token + **无效** refresh token 时，返回 401 但 access token 已被拉黑。

Java 版把校验全部前置，失败路径零写入。

**对前端不可见**：失败仍是同样的 `code 401` 与文案。Node 侧此行为未被任何测试覆盖，且它自己的 `plans/security-remediation.md` 的 Task 5 正是要修这个（未实施）。

## 11. 风险与未验证项

| # | 风险 | 应对 |
|---|---|---|
| 1 | **自己实现 SigV4 POST policy 签名** —— Java SDK 无此能力（[#1493](https://github.com/aws/aws-sdk-java-v2/issues/1493)、[#6577](https://github.com/aws/aws-sdk-java-v2/issues/6577)） | 用 Node 侧同一组输入产出参照值，断言 base64 `policy` 与 `x-amz-signature` **逐字节相同**。不通过不算完成 |
| 2 | **bcrypt `$2b$` 兼容性** | Spring Security 5.2+ 声称支持，但有过 `$2a` 正则的已知 issue。必须实测，不实测不认 |
| 3 | **`TRUST_PROXY` 语义等价** | Node 的 `loopback` 行为精确且是限流正确性的前提；Spring/Tomcat 的等价配置需实测对比 |
| 4 | Spring Security 默认行为泄漏破坏契约 | §8 的契约测试兜底 |
| 5 | MinIO 客户端配置差异（`forcePathStyle`、checksum 策略） | 照搬 Node 侧配置（`forcePathStyle: true`、checksum `WHEN_REQUIRED`）并实测上传 |
| 6 | 时区/时间格式漂移 | §3.1 的映射 + 契约测试断言 `createdAt` 的确切格式 |
| 7 | 删 Mongo/Redis 依赖的连带破坏 | 见阶段 0 的依赖链表：`TestcontainersConfiguration` 的两个 `@Bean` 会**编译失败**，不是运行时才暴露 |

## 12. 明确不做

- 令牌家族 / 重放检测（Node 亦无）
- refresh token 的 Cookie 双轨下发（Node 亦无）
- 按用户配额（Node 亦无）
- 多实例部署（因此**不需要 Redis**）
- `RateLimit` 响应头复刻（已确认前端不读）
- 现有 SQLite 数据迁移（已确认建空库）
